# ADR-0003 · 十进制字符串作为金额权威表示

> 状态：已接受 · 日期：2026-10-23

## 背景

价格是这个站点对用户最有价值、也最容易算错的部分。

具体的失败场景：

```js
0.1 + 0.2 === 0.30000000000000004   // 浮点误差
```

在阶梯价判断上这会直接算错钱：
「输入 token < 32000 且输出 ≥ 200 时按 ¥3.000 计价」——
用浮点比较，`31999.9999` 与 `32000` 的归类可能翻转。

更隐蔽的是**累加**：一张账单 100 万次 `0.1` 的加法，
浮点误差会累积成可见偏差。

还有一个语义问题：`null`（未取得可信值）与 `"0"`（确认免费）
如果都用 `0` 表示，下游**无法区分**「这个模型免费」和「这个模型价格没查到」。
用户按错误假设做成本规划。

## 决策

**金额的权威表示是十进制字符串。**

| 项 | 决定 |
|---|---|
| 存储 | `"3.00"`（字符串） |
| 比较 | `compareDecimal(a, b)` → -1/0/1（纯字符串运算，**不经过 `Number`**） |
| 累加 | `addDecimal(a, b)` |
| 展示 | 源金额保留完整精度；界面按十进制四舍五入并固定显示三位小数，小于半毫单位的正数显示为 `<0.001` |
| 未知 | `null` |
| 确认免费 | `"0"` |
| 数字字面量 `3` | **非法**——校验器拒绝 |

配套规则：
- `currency` 是**官方原始结算币种**，不从显示地区推断。
- **不做**「除以猜测汇率」的逆推。
- 不同币种**严禁**直接比较数值。

## 备选方案

### A. 整数最小单位（cents）

```json
{ "amount_minor": 300, "scale": 2 }
```

**不选**：可读性差，review 时人眼看不出「3.00」；
不同币种的小数位差异（USD 2 位、JPY 0 位、KWD 3 位）增加复杂度。
字符串方案在可读性与精度之间平衡更好。

### B. 用 JS `number`

**不选**：见上文的浮点误差。这不是「小问题」——
它是**在钱的计算上出错**。

### C. 引入 Decimal 库（如 decimal.js）

**不选**（当前）：增加运行时依赖。
十进制加减乘比较的字符串实现约 60 行，够用且零依赖。
**但如果**将来需要更复杂的运算（累计、舍入策略、货币格式化），
可以替换实现而不改数据格式——这是选字符串表示的额外好处：
**表示与实现解耦**。

### D. 金额用整数 + 单位固定

**部分不选**：Token 类计费确实适合整数（如每百万 token 的价格存成
「每亿分之一元」），但图像/视频/字符计费需要小数，
强行取整会引入新的误差源。

## 后果

**好处**：
- 金额计算**精确**，无浮点误差。
- 审阅时人眼可读（`"3.00"` vs `300`）。
- `null` / `"0"` 语义清晰，下游能正确区分。
- 表示与实现解耦，将来换 Decimal 库不影响数据。

**代价**：
- JSON 里金额是字符串，消费方**必须**显式解析——
  直接当数字用会出错（这是**刻意的**：强制消费方意识到精度问题）。
- 排序、聚合需要显式转换。
- 需要自己实现 `toScaledInt` / `fromScaledInt`——
  超大金额会超出 `Number.MAX_SAFE_INTEGER`。
  **当前价格量级远低于该限制**，但金额累加到极大值时需注意。

**新增的约束**：
- 金额字段必须匹配十进制字符串正则，负数被拒绝。
- 校验器对 `currency` 做 ISO 4217 三字母检查。
- 风险分级里的「价格波动 > 30%」判断**必须在同币种内**进行。
