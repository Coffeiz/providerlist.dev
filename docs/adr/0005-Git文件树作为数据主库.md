# ADR-0005 · Git 文件树作为数据主库

> 状态：已接受 · 日期：2026-10-23

## 背景

数据规模预估：

- Provider：首版 10–20 家，长期可能数百家
- Offering：每家数十到数百条
- Service / Endpoint：每家几条到几十条
- Source / Evidence：与字段数量同量级

**单 Provider JSON 大约 20–60 KB**，全量首版在 1–3 MB 量级。

关键需求：
1. **可评审**——审核者要能看清「改了什么」。
2. **可追溯**——每条数据能追到源头。
3. **可重建**——公开 JSON 能从源数据 + 工具链重建。
4. **可回滚**——错误数据能快速撤回。

## 决策

**Git 文件树作为数据主库。**

```
data/
├── providers/     # 每个 Provider 一个 JSON 文件
├── overrides/     # 人工核实差异层
├── provenance/    # 字段级证据
├── lifecycle/     # 供应事件
└── upstream/      # 上游快照指针与元数据
```

- 源数据是**可评审的小文件**（每个 Provider 一个文件，
  大型 Provider 再按 Service 拆分以减少 Git 冲突）。
- 生产目录（`dist/v1/**`）由**编译生成**，不手工编辑。
- 人工数据用 JSON / JSONC（需要注释时用 JSONC；
  **公共 Schema 与运行时统一纯 JSON**）。

## 备选方案

### A. PostgreSQL + 后台编辑界面

**不选**（当前）：
- 「可评审」需要额外的 diff 视图；Git 的 diff 是免费且成熟的。
- 「可追溯」变成应用层功能；Git 的 blame 是免费且成熟的。
- 需要额外的数据库、迁移、备份运维。
- 引入后台编辑后，**权限与审核流程**要重新设计（谁可以改什么、怎么审批）——
  这是完全独立的一大块工程。

**不选的代价是诚实的**：将来如果真的需要复杂后台编辑、
多用户协作、高频查询，这是升级信号。

### B. 全部塞进一个大 JSON

**不选**：Git 冲突粒度是整个文件——两个 Provider 的无关改动会冲突。
review diff 也没法看。

### C. SQLite / 纯文件二进制格式

**不选**：不可 diff，不可评审，不可手工编辑。

### D. TOML 替代 JSON

**可以**（团队偏好时可切换），但当前选 JSON：
- 公开 API 只能纯 JSON——人工数据用 TOML 意味着要写转换器。
- JSONC 已能满足「人工加注释」的需求。
- JSON 生态工具（Schema 校验、格式化、jq）更成熟。

## 后果

**好处**：
- 评审天然：PR diff 就是数据 diff。
- 追溯天然：`git blame` 回答「这行是谁什么时候改的」。
- 可重建：CI 从 `data/` + 工具链版本重建 `dist/`。
- 可回滚：`git revert` 就是数据回滚。
- 无额外基础设施。

**代价**：
- **不能把每天的 HTML 大快照无上限提交到 Git 主分支**——
  要用 GitHub Artifacts / Release 或受控对象存储归档，
  并记录 SHA-256 与可追溯指针。
- 检索依赖预构建索引，不依赖数据库查询。
- 大规模并发写入不是 Git 的强项——
  但本项目的写入是「PR 审核后合并」，不是并发写。

**新增的约束**：
- 自动抓取任务**不得覆盖**人工核实的数据（人工核实的定价差异归 `data/pricing/`）。
- 上游值与手工值必须**并存**并保留冲突解释。
- **禁止**从「公开 active 视图」反向写回完整数据仓库。
- 公开最终 JSON 仍应能从指定输入与工具链版本**重建**。
