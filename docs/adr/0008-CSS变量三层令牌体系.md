# ADR-0008 · CSS 变量三层令牌体系

> 状态：已接受 · 日期：2026-10-23

## 背景

这个站点同时有两个硬要求：

1. **数据密集**——表格、参数、约束、证据链，很多信息需要精确表达。
2. **支持亮/暗主题**——开发者长时间盯屏，主题切换是刚需。

同时项目要提供 `/design` 页作为设计系统的可视化出口——
它必须**不会与实现脱节**。

## 决策

**CSS 变量 + 三层令牌结构。**

```
原始层 primitive  →  语义层 semantic  →  组件层 component
```

- 原始层：色板与刻度，不表达语义。
- 语义层：把原始层映射到用途（表面、文字、边框、状态），
  **亮/暗两套值**。
- 组件层：具体组件，**只消费语义层**。

配套：
- 暗色通过 `html[data-theme='dark']` 覆盖**语义层与中性色阶**。
- 组件**不得硬编码颜色**。
- `/design` 页用 `getComputedStyle` **读取真实 CSS 变量**渲染——
  令牌改动立刻反映，不会与实现脱节。

### 修订（2026-10-23，见 ADR-0012）

原表述「暗色只改语义层，**原始层不变**」已不再成立。

中性色阶（`--pl-surface-*` / `--pl-ink-*`）在暗色下必须**整体翻转**——
否则语义层引用到的还是亮色那一档，深色主题会直接崩掉。所以暗色覆盖分成两段：
**中性色阶翻转**（原始层）+ **语义层重新映射**。

状态色阶不翻转，而是把「强」档换成亮色（保证文字对比度），
「弱」档换成半透明 tint（作为徽章底色）。

三层结构本身不变。

## 备选方案

### A. Tailwind

**不选**（当前）：
- Tailwind 的原子类让「这个颜色是什么语义」在代码里不可见——
  `text-gray-500` 不如 `var(--pl-text-tertiary)` 表达意图。
- 需要构建期配置与 purge 策略。
- 设计系统要另建配置体系，**两套东西**。

**升级信号**：组件数量增长到需要严格约束、或多人协作时 Tailwind 的
lint 规则优势更明显。

### B. CSS-in-JS

**不选**：
- 运行时开销与构建复杂度。
- 令牌与主题切换会变成 JS 逻辑，而不是一行 CSS 变量。
- 与「静态优先」的整体取向不符。

### C. 单一层令牌（只有语义色，没有原始层）

**不选**：调色时没有可用的中间色阶，
容易出现「加一个 `bg-gray-135`」这类失控。

### D. 组件库（Element Plus / Naive UI）

**不选**：
- 这个站点的视觉高度定制化（数据表格、约束展示、
  证据链层级），组件库的默认样式要大量覆写。
- 组件库带来完整但冗余的依赖。
- **不**照搬 Gugu-web 的 Glassmorphism 风格——
  那边是 ToC 产品，这边是工具型目录，风格刻意不同。

## 后果

**好处**：
- 暗色主题只改语义层，组件**零改动**。
- 语义名让代码自解释：`var(--pl-text-tertiary)` 比 `#9aa3b5` 有意义得多。
- `/design` 页是**真实值的渲染**，不是手工维护的副本。
- 零运行时依赖，构建产物小。

**代价**：
- 一次性要先定义完整的令牌体系，前期投入比直接写样式大。
- 缺少工具链约束——需要靠 review 保证「不硬编码颜色」，
  可以加静态扫描测试（CI 里 grep 颜色字面量）。
- 语义层需要**同时**维护亮暗两套，
  新增令牌时容易漏掉暗色值。

**新增的约束**：
- 新增语义令牌**必须**同时定义亮色与暗色两套值。
- 组件层**不写** `[data-theme='dark']` 选择器（除极少数特例）。
- 透明变体用 `color-mix()` 从语义令牌派生，
  **不**写死 `rgba(255,255,255,…)`。
- 改令牌后**必须**检查 `/design` 页显示与对比度。
