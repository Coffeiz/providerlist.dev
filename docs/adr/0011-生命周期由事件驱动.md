# ADR-0011 · 生命周期求值由事件驱动，参考时点取自证据

> 状态：已被 ADR 0041 取代（历史记录）

## 背景

设计文档 §9.1 的推荐目录里有 `data/sources/lifecycle/  # 供应事件`，
§14.2.1 的稳定 Schema 清单里有 `Lifecycle Event`，
§16.3 的验收用例写着「单一 API 返回缺少某模型：生成观察事件，
**不直接触发 retired**」。

但仓库里没有 `data/sources/lifecycle/` 目录，也没有 `LifecycleEvent` 类型——
生命周期状态是**手写内联**在 Provider 档案的 `lifecycle` 字段里的。
`pipeline/src/normalize/lifecycle.ts` 实现了状态机，却没有任何东西给它喂事件。

按 ADR-0009 的原则（不留空壳目录），要么完整接通，要么不建。已选择接通。

## 决策

### 1. 事件是观测层，档案是事实层

| 层 | 位置 | 性质 |
|---|---|---|
| 事实层 | `data/providers/*.json` 的 `lifecycle` | 上一次已核实的事实 |
| 观测层 | `data/sources/lifecycle/*.json` | 这次观察到了什么 |

`LifecycleEvent` / `AbsenceObservation` / `LifecycleEventDocument`
提升到**契约层** `@providerlist/schema`（§14.2.1 把它列入稳定 Schema），
`pipeline` 转发一份保持导入路径不变。

### 2. 状态由事件驱动，不由手改

构建流程：加载事件 → 交叉引用校验 → 状态机求值 → 落到已发布文档。

只有 `auto_publishable` 的结论才落盘。需人工复核的结论
（连续缺席达阈值、来源不完整）**保留上次可信状态**并报 warning——
绝不因为单次缺席或证据不足就改写已发布目录。

### 3. 参考时点取自证据，不取墙上时钟

这是本 ADR 最重要的技术决定。

`evaluateLifecycle` 原本内部用 `Date.now()` 判断「公告是否已生效」。
但 `data_version` 是**内容哈希派生**的：

```js
deriveDataVersion = `${datePart}.${sha256(documents).slice(0, 6)}`
```

同一天两次构建，若第二次的时间跨过了某个 `effective_at`，
产出内容就会不同，却**共用同一个版本号**——
直接违反「固定版本不可被覆写」这条不变量。

改法：求值时传入显式的 `referenceTime`，
由**该对象最新证据的观测时间**推导（事件与缺席观测的 `observed_at` 最大值）。

这同时更符合「未知就是未知」：我们没有 2027-04-01 之后的观测，
就不能断言 2027-03-01 的停服已经发生。状态是**证据支撑的**，
不是时钟推断的。

### 4. 状态没变就不动已发布记录

`observed_at` 的语义是「最近一次观测到**该状态**的时间」。
单次缺席没有观测到新状态，只是没看到它。
顺手把 `observed_at` 刷新成缺席时间，等于声称「那天我们观测到它还活着」。

所以：决策的 stage / announcement / retire_at 与当前一致时，
整个 `lifecycle` 原样保留，一个字段都不动。

### 5. 交叉引用必须成立

- 事件的 `subject_ref` 指向不存在的 Offering → **报错**。
  否则事件被静默忽略——那正是「不因单次缺席而退役」最容易被绕过的地方。
- `confirmed_retired` 没有 `evidence_refs` → **报错**。
  没有证据的停服不得进入已发布目录。

## 后果

**好处**：

- 生命周期有了**可追溯的来源**：状态不是手写的，是事件推出来的。
- 满足 §14.2.1 的稳定 Schema 清单与 §9.1 的目录结构。
- 满足 §16.3 的验收用例：缺席产生观察事件，不触发 retired。
- 构建可重现：同样的源数据 + 同样的事件 → 同样的版本、同样的内容。

**代价**：

- 事件层与档案层要保持一致。事件的 `subject_ref` 写错就是硬错误——
  这类错误在接入真实抓取前会频繁出现，但**报错比静默忽略好**。
- 求值逻辑从「看现在几点」变成「看最新证据」，
  意味着一个长期不更新的数据集不会自动反映「停服日已经过去」。
  这是刻意的：没有新证据就没有新断言。新鲜度由 `docs/data/data-policy.md`
  的新鲜度策略单独管理。
- 事件文件是新增的源数据层，接入真实抓取时需要同步实现写入方。

**新增的约束**：

- `data/sources/lifecycle/` **不得**手工编造事件来改变状态。
- 事件的 `subject_ref` 必须指向真实存在的 Offering。
- 停服事件必须带证据引用。
- 求值不得引入对墙上时钟的依赖（除非显式传入 `referenceTime`）。
