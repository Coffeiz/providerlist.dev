# ADR-0007 · 域名挑战作为授权锚点

> 状态：已接受 · 日期：2026-10-23

## 背景

官方接入需要判断「这个提交者是否真的代表这个 Provider」。

常见的直觉方案是看请求来源：
`Origin` 头、`Referer` 头、请求 IP、对方声称的 Provider ID。

**这些全部不可靠：**

- `Origin` / `Referer` 可以缺失（很多 HTTP 客户端不发）。
- 非浏览器请求可以任意伪造这两个头。
- CORS 是**浏览器**的机制，**不是**服务端鉴权。
- TLS 客户端通常只验证**服务端**证书，**不证明**调用者拥有任意域名。
- 厂商走 CDN / 对象存储，出口 IP 不是稳定的品牌身份。

## 决策

**用域名挑战作为授权锚点，且由服务端主动读取验证。**

两种方式，优先 HTTPS 文件、备选 DNS TXT：

```
https://<hostname>/.well-known/providerlist-challenge/<claim_id>
```

关键性质：
1. ProviderList **产生**高熵随机 `claim_id` + 短期有效 `nonce`，
   **服务端只保存 challenge 的哈希**与有效期。
2. Provider 在**待确认的域名**上部署 challenge。
3. ProviderList **主动**验证 HTTPS 证书、主机名、挑战正文 / TTL。
4. 挑战**一次性** `consumed`，短时有效。
5. 成功后明确绑定 `provider_ref` 和 `scope`（最小权限）。

**不能靠未经证明的 webhook callback 替代。**

配套：
- 域名是**授权锚点**，不是 Provider 本身。
- 一个 Provider 可有多个域名。
- 域名控制者**不当然**有权为同集团所有子公司或**其他 Provider** 发数据。
- 新品牌主体或委托域名需**人工确认**关联关系。
- 直接 Push 另行签发限权凭证——**域名不是运行时鉴权**。

## 备选方案

### A. 检查请求头（Origin / Referer）

**不选**：见上，全部可伪造或缺失。

### B. 检查请求 IP

**不选**：CDN 出口 IP 不稳定，且不能证明品牌归属。

### C. OAuth / 厂商账号登录

**不选**：要求厂商开设账号、注册应用、走审核——
接入门槛远高于域名挑战，与「低门槛接入」的目标冲突。

**不排除**：将来做多用户控制台时可叠加 OAuth 作为**第二因素**。

### D. 要求厂商上传文件到 ProviderList

**不选**：需要账号、需要存储、需要审核，
且不如「在你的域名放一个文件」自然。

### E. DNS 预解析后检查 IP 归属

**不选**：
- DNS 预解析一次**不能**认定安全——有 DNS rebinding、
  CDN 共享 IP、托管商动态分配。
- 权威归属需要 WHOIS / 证书透明度日志等额外信号，
  且这些信号**会过期**。

**保留**：DNS 预解析可作为**辅助信号**（例如判断是否指向已知的托管商），
但**不作为授权依据**。

## 后果

**好处**：
- 授权关系**可核实**（任何第三方都能独立验证 challenge 文件）。
- 厂商接入成本极低——放一个文件即可。
- 可撤销、可复核（`reverify_after`）。
- 不需要账号体系。

**代价**：
- 域名控制权会**过期**——域名到期、DNS 接管、CDN 配置失误。
  必须定期复核，过期后立即暂停授权。
- 品牌与域名的对应关系仍需**人工审核**（域名相似 ≠ 品牌归属）。
  「仅域名相似即可认领」的快捷路径**明确不做**。
- 委派、代运营场景需要额外的关系证明材料。

**新增的约束**：
- 域名挑战**不证明内容正确**——只证明控制权。
  「官方接入」徽章因此必须注明覆盖范围，且与「独立核验」分开。
- 域名控制权丧失时**立即撤销** AuthorizedDomain、Push 凭证
  与排队中未发布的提交；但**保留历史来源**。
- 每域 claim 频率限制、challenge 过期、重放与同形字防护。
