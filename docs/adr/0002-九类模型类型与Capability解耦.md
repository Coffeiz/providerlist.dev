# ADR-0002 · 九类模型类型与 Capability 解耦

> 状态：已接受 · 日期：2026-10-23

## 背景

「模型类型」这个概念在实践中被混用，导致三种典型错误：

1. **从类型臆测能力**——看到 `chat` 就展示「支持工具调用」，
   但那个模型可能不支持。
2. **把独立服务当模型**——把「网页搜索 API」包装成一个叫
   `web-search-model` 的模型，导致「模型数」虚高，且调用方按模型去接入会失败。
3. **把 Chat 内置工具当独立服务**——Chat API 的内置搜索工具与独立的
   `/search` 端点是两回事，统计与路由都会错。

## 决策

**三个概念独立建模：**

```
model_type  →  模型主类别（9 类标准值，兼容分类，单值）
Operation   →  这个供应项具体能做什么（可多个）
Capability  →  这个服务不依赖模型也能做什么（独立服务）
```

- `model_type` 是**开放枚举**——未知类型保留原值，报 warning，
  网站归入「其他」，**绝不**静默归并为 `chat`。
- `ServiceCapability` **不绑定模型**，**不计入** `active_offering_count`，
  `capability_id` 与 `offering_id` **命名空间独立**。
- Chat 内置 Server Tool 属于 `chat` Operation 的 `tools[]`，
  **不是**独立 Capability。若官方另提供独立搜索服务，**允许同时**记录两者。

## 备选方案

### A. 单一「能力」概念

所有东西都是 model + capabilities 列表。

**不选**：无法表达「这个服务不依赖任何模型」——
硬塞进 model 就得造假模型，统计与调用都会错。

### B. 严格闭集（只允许 9 类）

未知类型直接报错阻止发布。

**不选**：上游类型体系演进快。严格闭集会让新类型直接卡住发布，
迫使我们用错误的类型硬套——这比保留原值更糟。

### C. 从 model_type 自动推导 Operation

**不选**：这正是要避免的推断。`chat` 不一定支持 `structured_output`，
`video` 不一定支持 `image_to_video`。

## 后果

**好处**：
- 「模型数」「独立能力数」「Operation 数」三个统计口径清晰、可复算。
- 不会给接入方展示用不了的接口。
- 新模型类型出现时**不阻塞发布**。

**代价**：
- 数据录入更啰嗦——每个 Offering 要显式声明 `operation_ids`。
- 运营人员需要判断「这算模型还是算独立服务」——
  判据是**是否绑定模型**。
- 前端需要按类型切换列表字段（`chat` 显示 token 上下限，
  `video` 显示时长/分辨率，`speech` 显示音色/采样率）。

**新增的约束**：
- `operation_ids` 至少 1 个，且须有依据。
- 独立 Capability 不计入 `active_offering_count`。
- 未知类型**不阻止发布**——它必须能在网站降级展示为「其他」。
