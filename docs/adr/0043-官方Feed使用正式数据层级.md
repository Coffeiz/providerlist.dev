# ADR 0043：官方 Feed 使用正式数据层级

- 状态：已接受
- 日期：2026-11-01
- 更新：Service 市场字段改为由 Service ID 映射，见 [ADR 0046](0046-Service市场与Endpoint归属由层级确定.md)。
- 取代：[ADR 0035](0035-Well-known-Feed-URL候选发现.md) 中关于 Feed 正文声明 Service Scope 的格式约定；URL 发现和域名授权决策继续有效。

## 背景

Feed 示例曾将 `publisher`、`mode`、`scope` 和 `retirements` 放在顶层，并将 Offering、Route 和价格简化成与正式数据不同的形状。这让 Provider 难以对应仓库中的 Provider、Service、Offering、Plan 数据，也重复表达了服务端已经掌握的授权信息。

## 决策

1. Feed 使用 `provider`、`services`、`plans` 等正式领域对象，并沿用稳定 ID 与引用关系。
2. Offering 价格使用公开 API 的 `pricing` 结构；Plan 价格独立保存在 Plan 中。转换器负责将其转换为仓库内部 RateCard。
3. Feed 正文不包含 `publisher`、授权 Scope 或快照模式。Provider 身份、可写 Service 与字段由 ProviderList 的订阅和凭证记录决定。
4. Feed 仅更新明确提交的对象和字段。缺失记录不表示删除或退役；供应状态变化必须明确提交并经过校验与审查。
5. 当前 `feed-discovery` 只输出候选地址及 Provider 下已有 Service、Offering、Capability 和 Plan ID；它不抓取 Feed，也不授予权限。Feed 网络采集和转换器尚未实现。
6. Service 市场由市场目录 ID 映射；Feed 和 `service.json` 均不提交重复的市场字段、Provider ID 或 Service 名称。加载时由目录和市场字典生成这些字段。

## 备选方案

### 在 Feed 正文中继续携带 `scope` 和 `mode`

不选。授权属于 ProviderList 的接入配置；正文自行声明范围容易与服务端授权不一致，且不利于审阅。

### 用简化的 Offering 和价格结构

不选。Provider 需要把 Feed 字段映射回正式数据，重复维护对象身份、Service 归属和 Plan 分类会增加转换歧义。

## 后果

Feed 示例能直接对应 ProviderList 的领域对象，权限也有唯一服务端来源。实现 Feed 采集时，仍需增加独立的 Feed Schema、受限网络读取、授权校验、格式转换和候选审查；当前发现器不能被视为 Feed 采集器。
