# ADR-0001 · 静态公开数据与动态官方接入分离

> 状态：已接受 · 日期：2026-10-23

## 背景

项目要同时满足两个诉求：

1. **公众读**：任何人能快速、稳定地拿到当前供应目录。
2. **官方写**：Provider 能提交自己域名的数据，且提交要可控、可审计。

这两个诉求的**安全模型完全不同**：

- 读是**无认证、高并发、可缓存**的。
- 写是**有认证、低频、需要审计和限流**的。

如果放在同一个系统里（比如一个有数据库的 API 服务），
写路径的任何漏洞都会直接威胁公开数据的完整性。

## 决策

**读路径静态化，写路径独立。**

```
读：/v1/*.json  →  静态资源 + CDN     （无数据库、无鉴权、可缓存）
写：/api/v1/*   →  Worker + 队列      （鉴权、限流、持久化、审计）
```

连接方式：官方提交**先进候选**，经 CI 门禁后才生成新的静态 JSON。
**Worker 不直接写线上静态产物。**

## 备选方案

### A. 单一 API 服务 + 数据库

所有数据存在数据库里，网站调 API。

**不选**：
- 公开读依赖运行时数据库的可用性与性能——上游或数据库抖动会影响所有人。
- 读路径与写路径共享故障域。
- 缓存与 CDN 友好性差。
- 「已发布版本」难以保持不可变，审计困难。

### B. 全部走 Git PR（不做官方接入）

Provider 只能提 PR。

**不选**：
- 接入门槛高、更新慢，官方没有动力配合。
- 但**这仍是 P0 兜底路径**——官方接入未就绪时数据照常更新。

### C. Worker 同时处理读写

**不选**：路由上可以做到（`run_worker_first: ["/api/*"]`），
但仍应保持**逻辑隔离**——静态资源不经过 Worker 处理，
避免所有公开请求都进 Worker 执行（成本 + 性能）。

## 后果

**好处**：
- 公开读的可用性只依赖 CDN，与写入系统完全解耦。
- 读路径无鉴权负担，天然可缓存。
- 写路径的鉴权、限流、审计可以独立加固。
- 已发布版本天然不可变——它是 Git commit + 构建产物。

**代价**：
- 官方提交到上线**不是即时的**——必须经过队列 + CI。
  这是**特性而非缺陷**：高风险字段本来就需要人工审查。
- 需要维护两套部署配置（静态资源 / Worker）。
- 官方接入的实现复杂度明显高于纯 Pull 模式。

**新增的约束**：
- `202 Accepted` **绝不代表已上线**——对外文案禁止使用
  `pushed_successfully` 表示「上线」。
- 官方数据的 `last_seen_at` / `last_accepted_at` / `last_published_at` 是三个值。
- Provider 页面展示**最近成功发布**时间，不拿 HTTP 202 时间冒充上线。
