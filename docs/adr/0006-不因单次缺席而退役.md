# ADR-0006 · 不因单次缺席而退役

> 状态：已接受 · 日期：2026-10-23

## 背景

一个模型从供应商的模型列表里消失，可能有五种完全不同的原因：

1. 官方宣布停服了；
2. 官方宣布弃用，还没到停服日；
3. 上游接口故障 / 限流；
4. 我们的 API Key 权限被收窄了；
5. 抓取脚本的分页逻辑出了 bug。

**只有第 1 种是「退役」。**

如果按「扫不到就删」处理，一次上游抖动就会让网站上的模型大面积消失。
用户据此做的技术选型直接作废。

**这是最不可接受的失败模式**——比数据缺失严重得多。
数据缺失用户还能知道「查不到」，数据错误用户**不知道**。

## 决策

**退役判定必须由证据驱动。**

判定顺序（先匹配先生效）：

| 顺序 | 条件 | 结果 | 可自动发布 |
|---|---|---|---|
| 1 | 官方停服公告且 `effective_at` 已过 | `retired` | 有证据时 |
| 2 | 官方预告退役且未到 `effective_at` | `deprecated` | 是 |
| 3 | 官方宣布弃用（无停服日） | `deprecated` | 是 |
| 4 | 连续 ≥2 次完整列表缺失且跨 ≥24h | `unknown` | **否** |
| 5 | 本次来源不完整 | 保持原状态 + `stale` | **否** |
| 6 | 官方宣布恢复供应 | `active` | 是 |

关键阈值：

```js
ABSENCE_THRESHOLD = { min_consecutive_absences: 2, min_span_hours: 24 };
```

**这是可配置的运营参数，不是事实规则。**
达到阈值**也只升级为 `review_required`，不直接 retired**。

## 备选方案

### A. 缺席即退役

**不选**：一次上游抖动就能清空半个目录。

### B. 缺席即标记 unknown（立即）

比 A 好，但仍有问题：单次抓取失败就让几十个模型从
「已确认供应」变成「待核实」，噪声太大，用户体验劣化。

### C. 只在官方公告时才变状态，缺席完全不影响

**部分采纳**——这基本是我们的做法，
但我们额外保留了「连续缺席 → 待核实」的升级路径，
因为它能揭示「上游结构变了」这类真实问题。

### D. 用机器学习预测退役

**不选**：预测错误的代价是错误的退役判定，
而错误的**保留**代价只是信息稍旧。
这个不对称决定了应该保守。

## 后果

**好处**：
- 上游抖动不会污染生产目录。
- 退役信息可追溯——每条退役都有证据引用。
- 退役是 **Offering + Service + Route（按粒度）** 级别，
  不因某 Provider 停服就删掉 canonical 模型。

**代价**：
- 退役信息**滞后**——需要人工复核才能真正下线。
- 需要维护「待核实」分区，UI 复杂度增加。
- 阈值需要运营调优：太低会产生大量待审核项，
  太高会延迟发现真实退役。

**新增的约束**：
- `stage=retired` **必须**有 `evidence_refs`（校验器强制）。
- `deprecated` 在默认视图**继续显示**并有清晰提示。
- `unknown` **不计入**「已确认供应」计数，但可在「待核实」筛选中出现。
- 官方 Feed 的 `coverage=partial` **绝不构成缺失即删除**。
- 已授权 Feed 显式提交 `retire` 时，仍需 Scope / 冲突 / 时间规则满足
  才可按政策自动退役。
