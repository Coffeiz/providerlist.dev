# ADR-0004 · 约束 DSL 与计费条件语义隔离

> 状态：已接受 · 日期：2026-10-23

## 背景

多模态 API 的参数**不是独立枚举的笛卡尔积**。
一个真实的视频 API 可能这样规定：

- 可选时长 5 秒或 10 秒；
- 可选分辨率 720p 或 1080p；
- **但 1080p 只能选 10 秒**。

如果把 `resolution` 和 `duration_seconds` 渲染成两个独立下拉框，
用户就能选出 `1080p + 5s`——服务端必然拒绝的组合。

所以需要一套规则 DSL 来表达组合限制。

**但同时**，价格也需要条件表达：
「输入 < 32000 且输出 ≥ 200 时按 ¥3.00 计价」。

## 决策

**两套 DSL，两套语义，即使能共享解析器也严格隔离。**

| | `ConstraintRule` | `PriceRule.conditions` |
|---|---|---|
| 判断什么 | 请求是否合法 | 该收多少钱 |
| 字段域 | Operation 的 `parameters` / `input_slots` | 用量、计划、地区、时间等计费轴 |
| 形态 | `{ eq: ["resolution", "1080p"] }` | 条件数组元素 `{ field: "usage.input_tokens", operator: "lt", value: 32000 }` |
| 变化影响 | 改变请求合法性 | **不得**改变请求合法性 |

**理由**：如果共用一套字段域，一次调价（比如把「输出 ≥ 200」改成
「输出 ≥ 500」）就可能让某些参数组合突然「非法」——
这是极难排查的 bug，而且没有任何业务理由。

## 备选方案

### A. 共用一套条件 AST

**不选**：见上。价格变更会隐式改变请求合法性。

### B. 用 JSON Logic 或通用表达式库

**不选**：虽然表达力强，但——
- 无法静态分析「字段引用是否指向已声明的参数」；
- 引入了**数据驱动的表达式执行**，与「声明式数据，不执行代码」的原则冲突；
- 第三方库的行为边界需要额外审计。

### C. 用字符串脚本（如 `"if resolution == '1080p' then duration == 10"`）

**不选**：
- 需要 eval/解析器 → 注入风险。
- 无法静态分析循环依赖与不可满足性。
- 评审时人眼难以验证。

### D. 只在文档里写限制，不结构化

**不选**：那就是本项目要解决的问题本身。
自动生成 GUI 一定会渲染出非法组合。

## 后果

**好处**：
- 非法组合在 GUI 与只读 SDK 中**同时**被阻止，两侧行为一致。
- 价格变更**不会**意外改变请求合法性。
- DSL 是有限 AST，**可静态分析**：能检测循环依赖、
  永远不可满足的规则、未声明的字段引用。
- 语义清晰，两套 DSL 各自演进互不干扰。

**代价**：
- 两套 AST 要维护两套解析器（形态不同但可共享求值框架）。
- 表达力有上限——无法用规则表达「如果用户在 30 天内调用超过 1000 次
  则必须启用 X」这类依赖运行时状态的逻辑。
  遇到这种情况标 `manual_adapter_required`，由真实客户端实现适配。

**新增的约束**：
- DSL 只接受 `all/any/not/eq/in/lt/lte/gt/gte/requires/excludes`。
  **不接受**字符串脚本、任意正则执行器或外部可执行表达式。
- 字段引用只可指向**已声明**的参数/slot；
  引用未声明字段 → **阻止发布**。
- 未知操作符、循环依赖、永远不可满足的规则 → **阻止自动发布**。
