# ADR-0009 · demo 独立于生产站点

> 状态：已接受（**目录部分已被 [ADR-0013](0013-目录结构升级-frontend-pipeline-shared.md) 取代**） · 日期：2026-10-23
>
> 2026-10-23 修订：前端已从 `demo/` 迁到 `frontend/`（正式站点）。
> 本 ADR 的**核心约束仍然有效**——前端不读 `data/`、不提供示例回退、
> 演示数据必须是虚构的；被取代的只是目录形态与包名。

## 背景

设计文档 §9.1 的推荐目录结构里，网站在 `apps/web/`。

但项目当前阶段是 **M0/M1（研究与原型）**：
需要快速验证信息架构、交互与设计系统，
但数据契约、官方接入、SDK 都还没稳定。

如果现在就建 `apps/web/`，会出现两个问题：

1. **空壳目录**——`apps/web/` 里只有个 README，
   看起来像有，实际不能用。
2. **两份前端**——真写起来会有 `frontend/` 和 `apps/web/` 两套代码，
   然后要维护两份。这是明确的浪费。

## 决策

**`frontend/` 是当前唯一的前端实现，是独立可运行的项目。**

```
demo/
├── package.json      # 独立依赖，不与根 workspace 耦合构建
├── vite.config.ts
├── src/
│   ├── views/        # 页面
│   ├── components/   # 组件
│   ├── data/         # 数据层（消费 /v1/*.json）
│   ├── styles/       # tokens.css + base.css
│   └── router/
└── dist/
```

特点：
- **独立 `package.json`**，可以单独 `cd frontend && pnpm install && pnpm dev` 跑起来。
- 消费 `/v1/*.json` 静态产物——**不直接读 `data/`**，
  保证它验证的是**真实契约**而不是内部实现。
- 开发时通过 vite 中间件把根目录的 `dist/v1/**` 挂到 `/v1`。
- 构建时把同一份产物复制进 `frontend/dist/v1/`（`providerlist-catalog-copy` 插件），
  使站点产物**自包含**——否则部署后 `/v1/*.json` 全部 404，页面会静默变成空列表。
  缺 `dist/v1` 时构建直接失败并提示先跑 `pnpm build:catalog`。
- 不引入 Pinia、不引入 UI 框架、不引入 CSS-in-JS。

`apps/web/` **暂不创建**。生产化时把 `frontend/` 迁过去。

### 关于数据不可用时的行为

demo **不提供内置种子数据或示例回退**。加载失败时页面显示显式的错误空态
（`DataUnavailable` 组件），统计位显示「—」而不是「0」。

理由：目录站的取值必须可溯源。把「未取到」渲染成「不存在」会让读者
误判供应情况，比明确报错更危险——对应设计文档里「未知不等于没有」这条不变量。

## 备选方案

### A. 直接在 `apps/web/` 建

**不选**：见上——当前阶段会产生空壳目录或双份前端。

**升级信号**：M2 之后、开始接真实 SEO 需求（Provider 详情页需要被搜索引擎索引），
那时应把 `frontend/` 迁到 `apps/web/` 并考虑 Astro 静态预渲染。

### B. demo 做成纯静态 HTML（无构建）

**不选**：
- 需要手写模板拼接，组件复用困难。
- 路由、状态管理都要手写。
- 无法用 Vue 的 SFC 组织复杂页面。

### C. demo 与 apps/web 共用代码，通过配置区分

**不选**：过度设计。当前只有一份前端。

### D. demo 不消费 `/v1`，直接读 `data/`

**不选**：那样 demo 验证的是**内部数据结构**，
而不是**公开契约**——契约改了但 demo 照样跑，验证就失效了。

## 后果

**好处**：
- 没有空壳目录，没有双份前端。
- demo 独立可跑，任何人都能 `cd frontend && pnpm dev` 看效果。
- demo 消费真实编译产物，**端到端验证**了公开契约。
- 设计系统（`/design` 页）可以先在 demo 里成熟，再迁到生产站。

**代价**：
- 与设计文档 §9.1 的推荐结构**不一致**——
  这是**有意的偏离**，本 ADR 就是记录这个偏离的理由。
- 迁移到 `apps/web/` 时需要调整 import 路径与构建配置。

**新增的约束**：
- `frontend/` **不得**读 `data/` 目录——只读 `/v1/*.json`。
- 演示数据必须是**虚构的**——不代表任何真实厂商的供应或报价。

## 修订：类型与词典不再手抄（2026-10-23）

初版决策里 demo 保留了一份**精简的类型副本**（`frontend/src/types.ts`），
理由是「让 demo 独立可跑」。这个理由站不住，而且已经造成实际损害：

- **两份类型可以静默漂移。** 没有任何机制能发现 schema 改了而 demo 没改。
- **它已经漂移了。** demo 手写的模型类型标签把「图像生成 / 编辑」缩成了
  「图像生成」、「视频生成 / 编辑」缩成了「视频生成」——
  站点显示的名字和契约定义的不一致。
- **它让 demo 不再验证真实契约。** demo 消费的就是 schema 产出的 `/v1/*.json`，
  类型不同源，等于用「看起来对」的近似去验证契约。
- 「独立可跑」的收益很小：demo 本来就在 pnpm workspace 里，
  而且没有 catalog 产物也跑不出内容。

**修订后的决策**：

demo 直接依赖 workspace 包，不再维护副本：

```json
"dependencies": {
  "@providerlist/schema": "workspace:*",
  "@providerlist/shared/capabilities": "workspace:*",
  "@providerlist/shared/pricing": "workspace:*"
}
```

- `frontend/src/types.ts` 变成**转发层**，
  保留 `from './types'` 的导入路径不变，但内容全部 `export type ... from '@providerlist/schema/types'`。
  这些是纯类型导入，编译后完全擦除，**不产生运行时依赖**。
- `frontend/src/composables/format.ts` 删掉手抄的五张词典
  （`MODEL_TYPE_LABELS` / `OPERATION_LABELS` / `UNIT_LABELS` /
  `METRIC_LABELS` / `CURRENCY_SYMBOLS`），改为调用上游：
  - 模型类型标签 → `@providerlist/schema/model-types` 的 `modelTypeLabel`
  - Operation 标签 → `@providerlist/shared/capabilities/operations` 的 `operationLabel`
  - 计费单位 → `@providerlist/shared/pricing/units` 的 `describeUnit`
  - 计量指标与货币符号 → `@providerlist/shared/pricing/units` 的 `METRIC_LABELS` / `CURRENCY_SYMBOLS`
- **账号市场标签仍留在 demo**：它是展示层口径，不属于数据契约。

**这条约束改写为**：

> 展示层**不得**手抄领域词典。模型类型、Operation、计费单位、货币符号、
> 计量指标一律从 `@providerlist/schema`、`@providerlist/shared/capabilities`、
> `@providerlist/shared/pricing` 取；demo 的 `types.ts` 只做转发，不做定义。

代价是 demo 不再能脱离本仓库单独安装。但 demo 本来就是本仓库的原型，
这个代价换来的是「类型与词典只有一个真源」，值得。
